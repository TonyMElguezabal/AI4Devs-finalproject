## Requirements
### Requirement: A sent clip request is shown while the clip is generating

While a scene's clip request is in flight, the scene representation SHALL include `videoRequest` with the provider's display name and model, the attempt number, the instant the request was sent and an estimate. The expanded scene details SHALL show them, with the elapsed time since the request was sent updated live, under the accessible name `Scene {index} clip request`. When the clip is complete or the scene has failed, `videoRequest` SHALL be absent.

#### Scenario: Clip generating

- **GIVEN** scene 3's clip request was sent at 12:04:10 as attempt 1 to RunningHub
- **WHEN** the User expands scene 3 at 12:07:40
- **THEN** the details show RunningHub, its model, attempt 1, sent at 12:04:10 and 3 min 30 s elapsed

#### Scenario: Retry

- **GIVEN** scene 3's first clip request failed and the second was sent at 12:30:00
- **WHEN** the User reads the details
- **THEN** they show attempt 2 and the 12:30:00 send time

#### Scenario: Clip complete

- **GIVEN** scene 3's clip is complete
- **WHEN** the User reads the details
- **THEN** no clip request block is shown

### Requirement: The estimate is calculated from earlier clips

The estimate SHALL be the median generation time of the successful clip requests already recorded for the same provider and the same requested duration, when there are at least 3 of them; otherwise the median over that provider's successful clip requests of any duration, when there is at least 1; otherwise there SHALL be no estimate. The representation SHALL carry the estimated seconds and how many clips it is based on. The page SHALL show the expected arrival time and the number of clips it is based on, "no estimate yet" when there is none, and "taking longer than estimated" once the elapsed time passes the estimate.

#### Scenario: Enough clips of the same duration

- **GIVEN** RunningHub has finished 10 s clips in 400, 500 and 600 s
- **WHEN** a 10 s clip request is sent at 12:00:00
- **THEN** the estimate is 500 s based on 3 clips, and the page shows an expected arrival at 12:08:20

#### Scenario: First clip ever

- **GIVEN** no clip has been generated by the provider
- **WHEN** a clip request is sent
- **THEN** the page shows "no estimate yet"

#### Scenario: Past the estimate

- **GIVEN** a request whose estimate was 500 s
- **WHEN** 520 s have elapsed
- **THEN** the page shows "taking longer than estimated" and the elapsed time keeps counting

### Requirement: The User can open the request as sent, without provider details

The scene details SHALL offer a collapsed view of the request body sent for the current clip request. It SHALL contain only the prompt, the duration and the resolution as sent, and the first-frame image named as `scene {index} image`. It SHALL NOT contain the provider's upload URL, endpoint, task id, headers, credentials, or any field not on this list, even if the provider adapter sent one.

#### Scenario: Open the request

- **GIVEN** scene 3's clip request was sent with its VIDEO instruction, 10 s and the configured resolution
- **WHEN** the User opens the request view
- **THEN** it shows a JSON object with `prompt`, `duration`, `resolution` and `firstFrame: "scene 3 image"`

#### Scenario: Unknown field from an adapter

- **GIVEN** an adapter returns a sent body with an extra field
- **WHEN** the scene is read
- **THEN** the extra field is not in the representation

### Requirement: The request survives a restart

The send time and the body of the current clip request SHALL be stored with the scene when the request is sent, so the status and the request view are the same after the application restarts.

#### Scenario: Restart while generating

- **GIVEN** a clip request sent at 12:04:10
- **WHEN** the application restarts and the User opens the session
- **THEN** the details still show the 12:04:10 send time and the same request body

### Requirement: The clip request shows the provider task and when it was last checked

While `videoRequest` is present, it SHALL also carry:
- `taskId`: the provider's task id of the current attempt, as returned by the provider when the request was sent.
- `lastCheckedAt`: the instant of the most recent check of that task that answered "still running", or null when the task has not been checked since the application started.
- `waitEndsAt`: the instant at which the scene fails if the task is still unfinished (the send time plus the clip wait ceiling), or null when the video stage has no time limit.

Each check that answers "still running" SHALL update `lastCheckedAt` and publish a fresh snapshot to the live stream. The expanded scene details SHALL show the task id, how long ago the last check was (updated live by the page's clock, or "Not checked yet" when null) and "Gives up at <time> if unfinished" when `waitEndsAt` is not null. A new attempt SHALL start with `lastCheckedAt` null, so a retry never shows the previous task's check.

#### Scenario: A clip being followed
- **GIVEN** scene 10's clip request was sent at 22:43:08 as task `abc123`, with a 2400 s ceiling
- **AND** the provider answered "still running" at 22:50:42
- **WHEN** the User expands scene 10 at 22:50:52
- **THEN** the details show task `abc123`, last checked 10 s ago and "Gives up at 23:23:08 if unfinished"

#### Scenario: The next check arrives
- **GIVEN** the details show last checked 10 s ago
- **WHEN** the provider answers "still running" again
- **THEN** the page receives a new snapshot and shows last checked 0 s ago without a reload

#### Scenario: After a restart
- **GIVEN** a clip in flight when the application restarts
- **WHEN** the User opens the session before the first check after the restart
- **THEN** the details show the same task id and "Not checked yet"
- **AND** after the first check they show how long ago it was

#### Scenario: A retry
- **GIVEN** scene 10's first task failed and a second task `def456` was sent
- **WHEN** the User reads the details before the second task's first check
- **THEN** they show task `def456` and "Not checked yet"

#### Scenario: No time limit
- **GIVEN** the video stage has no time limit configured
- **WHEN** the User reads the details of a clip in flight
- **THEN** `waitEndsAt` is null and no "Gives up at" row is shown

#### Scenario: Clip finished
- **GIVEN** scene 10's clip is complete or the scene failed
- **WHEN** the User reads the details
- **THEN** no task id, last check or wait end is shown, because `videoRequest` is absent

#### Scenario: The task id is not part of the request body
- **GIVEN** a clip request in flight with task `abc123`
- **WHEN** the User opens the request as sent
- **THEN** the body shown contains only the prompt, the duration, the resolution and the first frame named `scene {index} image`, and no task id
- **AND** the provider's upload URL, endpoint and credentials appear nowhere in the read or the snapshot
