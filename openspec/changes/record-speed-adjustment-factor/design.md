# Design — Record requested duration and speed-adjustment factor per scene

## Context

`request-admitted-clip-duration` (JOS-147, merged) already computes, at registration, the admitted duration needing the smallest speed change to match a chunk's narrated interval, and stores `requested_duration_seconds` / `duration_warning` in the same transaction as the interval, locked by triggers (migration 10). It deliberately stops there: `docs/data-model.md` and `docs/backend-standards.md` both name this story (JOS-148) as the one that evaluates the resulting ratio against the acceptable limit and records the warning, once `SPEED_FACTOR_LIMIT` is available. `generate-chunk-video` (JOS-146)'s own proposal independently lists the same split in its "Out of Scope" section, so this boundary is already a settled, cross-checked decision, not a new one this design introduces.

The one open dependency is `SPEED_FACTOR_LIMIT` itself: it is `"undetermined"` in `backend/src/config/providers.ts` on this branch. The real value (fixed by `define-provider-configuration`/JOS-165 from `define-media-assembly`/JOS-182's measurement) exists only on JOS-182's unmerged pull request.

## Goals / Non-Goals

**Goals:**
- Specify exactly when and from what the speed-adjustment factor is computed, so it is never treated as a value chosen independently of the duration-selection rule (§7.2 is explicit that it is not an independent parameter).
- Specify that the factor and its warning are stored and locked at registration — the same transaction and the same convention JOS-147 already established for `requested_duration_seconds`/`duration_warning` — rather than derived on each read or computed later from an actual generated clip.
- Specify how the new fields are exposed on the existing session/scene representation, with no new endpoint and no dependency on `generate-chunk-video` (JOS-146) having run.

**Non-Goals:**
- Fixing or measuring the real `SPEED_FACTOR_LIMIT` value — owned by `define-provider-configuration` (JOS-165) and `define-media-assembly` (JOS-182). This story consumes the constant once it is no longer `"undetermined"`.
- Redesigning the scene-details panel or `US-19` (JOS-151, not started)'s broader "view per-scene status and results" work. This story only adds its three fields to the panel that already exists in `SceneRow.tsx`.
- Anything about the actual video clip (provider call, stored file, `video-generating` transition) — `generate-chunk-video` (JOS-146)'s scope, explicitly excluded from this one.

## Decisions

**Decision 1 — The factor is the `speedRatio` `closestAdmittedDuration` already computes when `requestedClipDuration` picks the requested duration; `requestedClipDuration` is extended to return it, rather than a new function recomputing the same formula from scratch.**
`closestAdmittedDuration(narratedSeconds, admitted)` (`admittedDurations.ts`, JOS-140) already returns `{ admitted, speedRatio }`, where `speedRatio = max(admitted / narrated, narrated / admitted)` — exactly the ratio §7.2 calls the speed-adjustment factor. `requestedClipDuration` (JOS-147) calls it and today keeps only `admitted`/`warning`, discarding `speedRatio`. This story adds a `factor: number` field to `RequestedClipDuration` and has `requestedClipDuration` pass `speedRatio` through unchanged, instead of a second function (e.g. `speedAdjustmentFactor(requested, narrated)`) that would recompute the identical formula from the already-selected duration — a repeated-pattern this design corrects before it ships, per the project's own "detect and highlight repeated code patterns" standard. Both inputs are final and locked before any provider is ever called, so the factor is available in the same registration step as JOS-147's write, with no dependency on `generate-chunk-video` reaching `chunk-complete`.
*Alternative rejected:* computing the factor from the video provider's actually-returned clip length (`admittedDurations.ts`'s own comment notes real clips land slightly off the nominal request, e.g. a requested 5 s clip measuring 5.17 s). §7.2 explicitly frames the factor as resulting from segmentation and duration selection, not from the provider's output, and computing it post-generation would make a scene's recorded factor depend on `generate-chunk-video` having run — reintroducing exactly the coupling JOS-146's proposal and `docs/data-model.md` both already ruled out when they scoped this story apart from it.
*Alternative also rejected:* a standalone `speedAdjustmentFactor(requestedDurationSeconds, narratedDurationSeconds)` function, as originally planned before implementation started. It would recompute `max(a/b, b/a)` a second time from values `closestAdmittedDuration` already derived in the same call, risking the two drifting apart (e.g. a future tie-break or rounding change to one and not the other) for no benefit over threading the existing value through.

**Decision 2 — Both `speed_factor` and `speed_factor_warning` are stored and locked at registration, mirroring JOS-147's `requested_duration_seconds`/`duration_warning` pattern exactly.**
`registerDecomposition` calls the Decision 1 function right after `requestedClipDuration` returns, and `insertRegisteredScenes` writes `speed_factor` and `speed_factor_warning` in the same transaction and the same migration-10-style lock triggers (migration 11). `speed_factor_warning` is set only when the factor exceeds `SPEED_FACTOR_LIMIT` in effect at registration, and a later build with a different limit must not reinterpret an already-established chunk — the same guarantee JOS-147's own spec already states for the admitted-durations set.
*Alternative rejected:* deriving `speed_factor` on every read instead of storing it. The number itself is a pure function of two already-locked values and could safely be recomputed, but `speed_factor_warning` cannot be (it depends on an external, buildable-changeable constant) — storing one and deriving the other would leave an inconsistent pair and a second code path computing part of the same value. Storing both together keeps the chunk's recorded result self-contained and matches the project's "every per-chunk derived value chosen at registration is stored and locked, never recomputed" convention (`docs/base-standards.md` §"store-enforced locks").

**Decision 3 — This extends the existing `clip-duration-request` capability rather than introducing a new one.**
The factor is computed in the same function call, the same transaction, and from the same inputs as JOS-147's already-spec'd requirement ("The requested duration is stored with the chunk and never changes"); splitting it into a separate capability would duplicate that requirement's locking and exposure language for no behavioral reason.
*Alternative rejected:* a new `speed-adjustment-factor` capability, mirroring how `generate-chunk-video` introduced its own new capability for video fields. That precedent doesn't transfer here: video fields are populated later, by a different stage, in a different transaction, which justified a separate capability there. This story's fields are populated in the very same transaction as an existing one.

**Decision 4 — `SPEED_FACTOR_LIMIT` is `2.0`, the unsigned mapping of `define-media-assembly`'s (JOS-182) 0.5×-2.0× recommendation.**
ADR 0005 Decision 5 (Accepted, 2026-09-26) measured the underlying ffmpeg retiming *mechanism* as sharply asymmetric by direction (speed-up: 0% duplicate frames up to 2.0×; slow-down: duplication growing as `1 - rate`, reaching 50% at 0.5×), but its own "Design open questions, answered" §2 states the recommended *numeric range* is **not** asymmetric: 0.5× (floor) and 2.0× (ceiling) are reciprocals, and this story's factor is the unsigned `max(requested/narrated, narrated/requested) ≥ 1` — so `1/0.5` and `2.0/1` both land on the same unsigned value, 2.0. One scalar limit on the unsigned factor is sufficient; no direction-aware comparison (i.e. branching on whether the chunk was sped up or slowed down) is needed.
Implementation initially gated here: `SPEED_FACTOR_LIMIT` was `"undetermined"` in `providers.ts` (JOS-165's own comment: "this change only records the number once [JOS-182] lands"), and JOS-182's pull request (#3) was still unmerged when this gate first ran. The user confirmed both JOS-182 and JOS-165 are done, so this story sets the constant directly — reading the real ADR rather than guessing, per the gate's own instruction.
*Alternative rejected:* a direction-aware comparison (two bounds, keyed off whether `requestedDurationSeconds > narratedDurationSeconds`). The reciprocal-mapping arithmetic above shows this is unnecessary for the recommended range specifically; it would also need a fourth field or a derived direction flag for no behavioral difference in the result.

**Decision 5 — The frontend fields land in the scene-details panel that already exists, not a new one.**
`SceneRow.tsx`'s `scene-details` `<dl>` already renders `Provider`/`Attempts` behind the same "View scene details" toggle, and its own comment names exactly this gap ("requested duration and speed factor in scene details ... US-15"). This story adds `requested_duration_seconds`/`speedFactor`/`speedFactorWarning` (and, since the backend already sends it, `durationWarning`) to `SceneEventPayload` in `frontend/src/types.ts`, and renders them as additional `<dt>`/`<dd>` pairs, shown only when present (a scene without a stored request renders none of them, matching the skeleton-scene case the spec already covers).
*Alternative rejected:* waiting for `US-19` (JOS-151) to build a distinct scene-details screen before showing these fields. Linear lists JOS-151 as a dependency, but the panel AC3 asks for already exists in the skeleton; waiting would leave the backend's work unreachable from the UI for no spec-required reason, and `SceneRow.tsx`'s own comment already expects this story to fill the gap, not a later one.

## Risks / Trade-offs

- **`SPEED_FACTOR_LIMIT`'s recommendation (ADR 0005) is itself flagged with open caveats** (synthetic `testsrc` fixture only, no real provider footage tested, the perceptual read is "a single AI agent's provisional read... not a human watching the sweep clips play") → this story consumes the number as recorded; revisiting it if real footage changes the recommendation is `define-media-assembly`'s/`define-provider-configuration`'s concern, not this one's.
- **A chunk could end up with `requested_duration_seconds` set but no `speed_factor`** if this story's write is ever separated from JOS-147's → Decision 2 keeps them in the exact same transaction specifically to make that state unreachable; a functional test asserts it.
- **Confusing `duration_warning` (`exceeds-maximum`) with `speed_factor_warning`** → they are independent booleans-in-effect on different causes (an unsplittable sentence vs. a factor over the hardcoded limit); a chunk can carry either, both, or neither, and the spec states this explicitly to prevent the two being collapsed into one warning field.

## Migration Plan

Nothing is deployed and no scene currently has a `speed_factor` value. Migration 11 adds `scenes.speed_factor` (`REAL`) and `scenes.speed_factor_warning` (`TEXT`), each with its own lock trigger, built from their own constants the same way migration 10's were. Rollback before implementation is deleting the change directory; no running session exists yet that a schema rollback would need to account for.
