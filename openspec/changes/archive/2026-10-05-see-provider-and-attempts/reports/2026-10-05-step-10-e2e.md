# Step 10: browser E2E (JOS-166, see-provider-and-attempts)

Date: 2026-10-05. Branch `feature/jos-166-see-provider-and-attempts`, HEAD `520db97`.

## 10.1 Applicability

Applies: scene details and phase sections change.

## Tool used, and why

The first attempt used the Claude in Chrome tools. The tab loaded the page, but `find`, `get_page_text` and `screenshot` all failed or timed out ("page busy"); after three failed calls I stopped and the product owner chose the `playwright-cli` skill instead. Everything below was done with `playwright-cli` (a fresh Chromium, run from a scratch folder outside the repository).

## 10.2 Setup and scene details

Backend on port 3100 (scratch store and project folder, `ALLOW_TEST_ENDPOINTS=1`, stub voice in `hang` mode, stub video `success`) and the frontend dev server on port 5173. A session was created, one scene was driven through its clip with `quick-scene`, and the image attempts and the session-level attempts were added to the scratch store with the backend's own store functions, with sentinel text in every free-text column (as in step 9). The page at `http://localhost:5173/?sessionId=<id>` showed, after expanding "View scene 1 details":

```
group "Scene 1 image diagnostics": "Image: Fal.ai (fal-ai/flux/dev), 2 attempts"
group "Scene 1 clip diagnostics":  "Clip: Stub provider (stub-video-provider), 1 attempt"
```

The Chromium accessibility snapshot shows each line as a group under its accessible name. Screenshot: `2026-10-05-step-10-scene-details.png`.

## 10.3 A count that rises without a reload

No stub image provider can be driven over HTTP (the image stage makes a real Fal.ai call), so instead of a transient failure followed by a success, a third image attempt record was added to the store while the page stayed open, and a pause followed by a continue made the backend publish a new snapshot. The same line then read `Image: Fal.ai (fal-ai/flux/dev), 3 attempts`, and the page still had a single navigation entry (no reload).
